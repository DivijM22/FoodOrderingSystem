# API Reference

Base URL (through the gateway): **`http://localhost:8080`**.
Locally, each service is also reachable directly: auth `:4001`, catalog `:4002`, order `:4003`, payment `:4004`, billing `:4005`, delivery `:4007`.
The Notification Service (`:4006`) is internal and not published. Use the gateway in anything a teammate or client will rely on.
New to the project? Start with [TEAM_HANDOVER.md](TEAM_HANDOVER.md).

## Conventions

**Authentication:** `Authorization: Bearer <accessToken>` (from `POST /auth/login`).

**Money:** every amount is an **integer number of paise** (₹249.00 → `24900`).

**Success envelope**

```json
{ "success": true, "data": { ... } }
{ "success": true, "data": [ ... ], "meta": { "page": 1, "limit": 20, "total": 16, "totalPages": 1 } }
```

**Error envelope**

```json
{
  "success": false,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Request validation failed",
    "details": [{ "path": "body.email", "message": "Invalid email address" }]
  }
}
```

| HTTP | `code` values emitted by the services (generated from the code, Stage 8) |
|---|---|
| 400 | `VALIDATION_ERROR`, `MALFORMED_JSON`, `INVALID_ID`, `BAD_REQUEST`, `INVALID_SIGNATURE` (webhook) |
| 401 | `MISSING_TOKEN`, `INVALID_TOKEN`, `TOKEN_EXPIRED`, `INVALID_CREDENTIALS`, `UNAUTHORIZED` |
| 403 | `FORBIDDEN` |
| 404 | `NOT_FOUND` (also for resources owned by someone else) |
| 409 | `CONFLICT`, `CONCURRENT_UPDATE`, `EMAIL_TAKEN`, `DUPLICATE_ITEM`, `PURE_VEG_VIOLATION`, `DISCOUNT_EXISTS`, `ORDER_NOT_CANCELLABLE`, `BILLING_PENDING`, `ALREADY_PAID`, `ORDER_EXPIRED`, `ORDER_NOT_PAYABLE`, `PAYMENT_PROCESSING`, `PAYMENT_IN_PROGRESS`, `AMOUNT_MISMATCH`, `REFUND_IN_PROGRESS`, `PAYMENT_NOT_REFUNDABLE`, `PAYMENT_NOT_INITIATED`, `INVALID_PAYMENT_STATE`, `IDEMPOTENCY_KEY_REUSED`, `AGENT_BUSY`, `DELIVERY_ALREADY_PICKED_UP`, `DELIVERY_ALREADY_ARRIVED`, `DELIVERY_NOT_PICKED_UP`, `DELIVERY_NOT_ARRIVED`, `DELIVERY_CANCELLED`, `ALREADY_DELIVERED`, `INVALID_DELIVERY_STATE`, `DELIVERY_NOT_RETRYABLE`, `OTP_NOT_ISSUED`, `CUSTOMER_EMAIL_MISSING` |
| 410 | `OTP_EXPIRED` |
| 413 | `PAYLOAD_TOO_LARGE` |
| 422 | `UNPROCESSABLE`, `RESTAURANT_NOT_FOUND`, `RESTAURANT_CLOSED`, `ORDER_ITEMS_INVALID`, `RESTAURANT_ID_REQUIRED`, `REFUND_EXCEEDS_REMAINING`, `PHONE_REQUIRED`, `OTP_INVALID` |
| 423 | `OTP_LOCKED` |
| 429 | `OTP_RESEND_TOO_SOON`, `OTP_RESEND_LIMIT` (and the gateway's rate limit on `/auth/*`) |
| 500 | `INTERNAL_ERROR` |
| 502 | `PAYMENT_PROVIDER_ERROR` |
| 503 | `SERVICE_UNAVAILABLE`, `CATALOG_SYNC_PENDING`, `CATALOG_SYNC_UNAVAILABLE`, `PAYMENT_PROVIDER_UNAVAILABLE` |

(Removed in Stage 8 because no code emits them any more: `INVOICE_NOT_READY`, `INVALID_STATUS_TRANSITION`, `USE_CANCEL_ENDPOINT`,
`ORDER_TOTALS_INVALID`, `CATALOG_UNAVAILABLE`, `ORDER_SERVICE_UNAVAILABLE`, `BILLING_SERVICE_UNAVAILABLE`.)

Every response carries an `x-request-id` header. Send your own to trace a request across services.

**Health:** `GET /health` on every service; through the gateway use `GET /health/auth`, `/health/catalog`, `/health/order`, `/health/payment`, `/health/billing` or `/health/delivery` (the Notification Service is internal; the dev console at http://localhost:3100 shows all seven).

```json
{ "status": "ok | degraded | unhealthy", "service": "order-service", "checks": { "mongo": "up", "rabbitmq": "up" } }
```

**Interactive docs:** Swagger UI at **http://localhost:3100/docs** (OpenAPI 3.1, [`docs/openapi.json`](docs/openapi.json), generated
from [`docs/openapi.mjs`](docs/openapi.mjs)). `node scripts/openapi.mjs check` verifies that the spec, the Express routes and the
gateway routes agree.

## Auth Service

| Method | Path | Auth | Description |
|---|---|---|---|
| POST | `/auth/register` | — | Register a **customer** |
| POST | `/auth/login` | — | Log in, receive a JWT |
| GET | `/auth/verify` | any | Validate a token, return its claims |
| GET | `/auth/me` | any | Current user's profile |
| PATCH | `/auth/me` | any | Update name, phone, saved addresses |
| POST | `/auth/me/password` | any | Change password (204) |
| GET | `/auth/users?role=&page=&limit=` | platform_admin | List users |
| POST | `/auth/users` | platform_admin | Create any role (e.g. restaurant admin, delivery agent) |
| PATCH | `/auth/users/:id/status` | platform_admin | Activate/deactivate a user (409 `LAST_ACTIVE_ADMIN` for the last active platform admin) |
| DELETE | `/auth/users/:id` | platform_admin | Permanently delete an **inactive** account (see below) |

### POST /auth/register

```json
{ "name": "Priya Sharma", "email": "priya@example.com", "password": "Priya1234", "phone": "9876543210" }
```

Password: 8–72 characters with at least one letter and one digit. Unknown fields (e.g. `role`) are rejected.
→ **201** with the public user (never includes a password hash). Duplicate email → **409 `EMAIL_TAKEN`** (case-insensitive).

### POST /auth/login

```json
{ "email": "priya@example.com", "password": "Priya1234" }
```

→ **200**

```json
{
  "success": true,
  "data": {
    "accessToken": "eyJhbGciOiJIUzI1NiIs...",
    "tokenType": "Bearer",
    "expiresIn": "1h",
    "user": { "id": "6ad0…", "name": "Priya Sharma", "email": "priya@example.com", "role": "customer", "...": "..." }
  }
}
```

Wrong password or unknown email → **401 `INVALID_CREDENTIALS`** (identical responses). Deactivated → **403**.

JWT claims: `sub` (user id), `email`, `name`, `role`, `iss=food-auth-service`, `aud=food-platform`, `exp`.

### PATCH /auth/me

```json
{
  "name": "Priya S",
  "phone": "9876543210",
  "addresses": [{ "label": "Home", "line1": "12 MG Road", "city": "Bengaluru", "pincode": "560001" }]
}
```

### POST /auth/users (platform admin)

```json
{ "name": "Ravi Kumar", "email": "ravi@food.local", "password": "Deliver123", "role": "delivery_agent" }
```

Roles: `customer`, `restaurant_admin`, `delivery_agent`, `platform_admin`.

### PATCH /auth/users/:id/status (platform admin)

`{ "isActive": false }` deactivates (publishes `auth.user.deactivated.v1`), `{ "isActive": true }` reactivates (publishes nothing). You
cannot deactivate yourself (403), and deactivating the **last active platform administrator** is refused with 409 `LAST_ACTIVE_ADMIN`.
Concurrent admin deactivations serialize on a lock document in `auth_db`, so two admins cannot deactivate each other at the same moment.

### DELETE /auth/users/:id (platform admin)

Permanently deletes an account. The account must be **deactivated first**. On success the user document is removed and
`auth.user.deleted.v1` is written to the outbox **in the same transaction**; the existing relay publishes it.

```json
{ "success": true, "data": { "id": "6ad3a1c2e4b5f60718293a4b", "role": "restaurant_admin", "deletedAt": "2026-10-26T12:00:00.000Z" } }
```

| Status | Code | When |
|---|---|---|
| 400 | `VALIDATION_ERROR` | `id` is not a 24-hex ObjectId |
| 401 | `MISSING_TOKEN` / `INVALID_TOKEN` / `TOKEN_EXPIRED` | no or bad token |
| 403 | `FORBIDDEN` | caller is not a platform admin |
| 403 | `CANNOT_DELETE_SELF` | the caller's own id |
| 403 | `ACTOR_NOT_ACTIVE` | the caller's admin account has since been deactivated or deleted (its JWT is still valid) |
| 404 | `NOT_FOUND` | no such account, including a **repeated** delete (no second event) |
| 409 | `USER_ACTIVE` | the account is still active: deactivate it first |
| 409 | `AGENT_HAS_ACTIVE_DELIVERY` | a delivery agent still holds an active delivery (Auth's event-fed projection); retry once it is completed or cancelled |

Protected accounts: the caller (always), and, through the inactive-before-delete rule plus `LAST_ACTIVE_ADMIN` on deactivation, the
last active platform administrator. Nothing in the request body is read, so no role or field can be changed through this endpoint, and the
response never contains password hashes. Ids are MongoDB ObjectIds and are never reused; the same **email** may register again later and
gets a new id. Orders, payments, refunds, invoices, ledger entries, delivery history and notification logs are **kept** and may still hold
the user id and the name, email and address captured at the time. This is not complete personal-data erasure.

## Catalog Service

Browsing is public. Management requires a `restaurant_admin` **assigned** to the restaurant (listed in its `adminIds`) or a `platform_admin`.

| Method | Path | Auth | Description |
|---|---|---|---|
| GET | `/restaurants` | — | List/search/filter restaurants (paginated) |
| GET | `/restaurants/cuisines` | — | Distinct cuisines |
| GET | `/restaurants/:id` | — | Restaurant details |
| GET | `/restaurants/:id/menu` | — | Menu + categories + restaurant summary |
| GET | `/restaurants/:id/menu/:itemId` | — | Single menu item |
| GET | `/restaurants/mine` | restaurant_admin | Restaurants assigned to the caller (incl. inactive), with `adminIds` |
| POST | `/restaurants` | **platform_admin** | Create restaurant (optional initial `adminIds`) |
| PATCH | `/restaurants/:id` | assigned restaurant_admin, platform_admin | Update details (`status` is platform-admin only; no assignment changes here) |
| PATCH | `/restaurants/:id/open` | assigned restaurant_admin, platform_admin | `{ "isOpen": false }`: operating status |
| DELETE | `/restaurants/:id` | platform_admin | Soft delete (status → inactive) |
| POST | `/restaurants/:id/admins` | **platform_admin** | `{ "userId": "…" }` assign an administrator (`$addToSet`, idempotent) |
| DELETE | `/restaurants/:id/admins/:userId` | **platform_admin** | Remove an administrator (`$pull`, idempotent) |
| POST | `/restaurants/:id/menu` | assigned restaurant_admin, platform_admin | Add menu item |
| PATCH | `/restaurants/:id/menu/:itemId` | assigned restaurant_admin, platform_admin | Update item (name, description, price, …) |
| PATCH | `/restaurants/:id/menu/:itemId/availability` | assigned restaurant_admin, platform_admin | `{ "isAvailable": false }` |
| DELETE | `/restaurants/:id/menu/:itemId` | assigned restaurant_admin, platform_admin | Delete item (204) |

**Restaurant administrators (many-to-many).** A restaurant stores `adminIds: string[]` (Auth user ids). A restaurant can have
several administrators and an administrator several restaurants; all administrators of a restaurant have **identical** permissions
(no owner/manager hierarchy). "Assigned" means the caller's JWT `sub` is in `adminIds` and their role is `restaurant_admin`; anyone else
gets **403** on management endpoints. Only platform admins create restaurants and change assignments. `adminIds` is returned only to
platform admins and to the restaurant's own administrators — never to customers or anonymous callers. Assignment ids are not checked
against the Auth Service (no synchronous call); the console only offers `restaurant_admin` accounts.

```json
{
  "name": "Momo Mania",
  "description": "Steamed, fried and tandoori momos with fiery chutneys.",
  "cuisines": ["Tibetan", "Momos"],
  "tags": ["Quick Bites"],
  "address": { "line1": "5th Cross", "area": "Kammanahalli", "city": "Bengaluru", "pincode": "560084" },
```

Platform admins only. Optional `"adminIds": ["6ad2…", "6ad3…"]` assigns the initial administrators (duplicates ignored); a restaurant

### POST /restaurants/:id/admins · DELETE /restaurants/:id/admins/:userId (platform admin)

```json
{ "userId": "6ad3a1c2e4b5f60718293a4b" }
```

Atomic and idempotent (`$addToSet` / `$pull`): assigning someone already assigned or removing someone not assigned changes nothing.
Both return the restaurant (with `adminIds`). Changes take effect immediately in the Catalog Service and reach the Order Service's
projection through `catalog.restaurant.updated.v2` (restaurant admins' order access follows within moments). Assigning the id of a
**deleted** account (known from `auth.user.deleted.v1`) returns 409 `USER_DELETED`; the same applies to `adminIds` in `POST /restaurants`.

### GET /restaurants/mine (restaurant admin)

The restaurants whose `adminIds` include the caller, sorted by name, including inactive ones, each with `adminIds`.

### POST /restaurants/:id/menu

```json
{ "name": "Chicken Steamed Momos", "category": "Momos", "price": 18900, "isVeg": false, "description": "8 pcs", "spiceLevel": 1 }
```

Pure-veg restaurants reject non-veg items (**409 `PURE_VEG_VIOLATION`**). Duplicate names within a restaurant → **409 `DUPLICATE_ITEM`**.

if any, is in a given database depends on how it was seeded (TEAM_HANDOVER §10).

## Order Service

All endpoints require authentication.

| Method | Path | Roles | Description |
|---|---|---|---|
| POST | `/orders` | customer | Place an order (optional `Idempotency-Key` header) |
| GET | `/orders` | customer (own), restaurant_admin (`?restaurantId=` of an assigned restaurant), platform_admin (all) | Order history (newest first) |
| GET | `/orders/:id` | owner / an administrator of the order's restaurant / platform_admin / the **assigned** delivery_agent | Order details, status history, delivery mirror |
| GET | `/orders/:id/tracking` | same as `GET /orders/:id` | Progress tracker: steps, delivery status, partner, timestamps, history |
| GET | `/orders/:id/tracking/stream` | same as `GET /orders/:id` | **Live tracking (Server-Sent Events)** |
| POST | `/orders/:id/cancel` | customer (own), an administrator of the order's restaurant, platform_admin | Cancel an eligible order |

There is **no endpoint that sets an order status**. Status changes come only from payment and delivery events,
validated by the Order Service (the former `PATCH /orders/:id/status` now returns 404).

### POST /orders

```http
POST /orders
Authorization: Bearer <customer token>
Idempotency-Key: checkout-7f3c9a21        (optional, 8–100 chars [A-Za-z0-9_-])
Content-Type: application/json

```

```json
{ "reason": "Ordered by mistake" }
```

| Actor | May cancel when status is |
|---|---|
| customer (own order) | `pending_payment`, `confirmed` |
| restaurant admin (assigned to the order's restaurant) | `pending_payment`, `confirmed`, `assigning_delivery_partner` |
| platform admin | `pending_payment`, `confirmed`, `assigning_delivery_partner`, `partner_assigned` |

Otherwise → **409 `ORDER_NOT_CANCELLABLE`** — in particular **nobody can cancel after pickup** (`out_for_delivery`, `location_reached`).
A paid order becomes `paymentStatus: "refund_pending"` and is refunded through the Payment/Billing events; the Delivery Service
cancels its delivery and releases the partner (`delivery.cancelled.v1`).
Side effect: `order.cancelled.v1` and `order.status_changed.v1` (status `cancelled`) are published.

### Order statuses

`pending_payment` → `confirmed` (payment verified) → `assigning_delivery_partner` → `partner_assigned` →
`out_for_delivery` → `location_reached` → `delivered`, plus `cancelled` and `expired`. Delivery steps come from
`delivery.*` events from the Delivery Service (`delivered` only after OTP verification). `preparing`, `ready_for_pickup`
and `payment_failed` appear only on historical orders.

### Expiry

An order still unpaid (`paymentStatus` `pending` or `failed`) at `expiresAt` is moved to status **`expired`**
by the expiration worker, with a `statusHistory` entry `{ status: "expired", by: "expiration-worker", role: "system" }`,
and `order.expired.v1` is published. Expired orders are terminal (cancel → 409) and are **never deleted**;
`GET /orders?status=expired` lists them. Configuration: `ORDER_PAYMENT_DEADLINE_SECONDS` (default 900),
`EXPIRY_SWEEP_INTERVAL_MS` (default 15000).

### Payment fields on orders (Stage 4)

`paymentStatus` mirrors the Payment Service and changes only from `payment.*` events (plus `refund_pending` set
at cancellation of a paid order). Its values are `pending`, `paid`, `failed` (the order stays `pending_payment`
and can be retried), `cancelled`, `refund_pending`, `partially_refunded`, `refunded` and `refund_failed`.
Orders also carry `paymentId` and an append-only `paymentHistory[]` of `{ eventType, paymentStatus, at, note }`.

## Payment Service

Gateway prefix `/payments`. Amounts are **integer paise**, currency **INR**. The active provider
(`stripe` = Stripe test mode, `mock` = local simulation) is reported as `provider` on every payment.

| Method | Path | Auth | Description |
|---|---|---|---|
| POST | `/payments/initiate` | customer | Create or resume payment for an order; returns the PaymentIntent client secret |
| GET | `/payments` | customer (own), platform_admin (all; `?customerId=`) | List payments (`?status=&orderId=&page=&limit=`) |
| GET | `/payments/order/:orderId` | owner, platform_admin | Payment for an order (with refunds) |
| GET | `/payments/:id` | owner, platform_admin | Payment details, status history and refunds |
| POST | `/payments/:id/refund` | platform_admin + `Idempotency-Key` | Full or partial refund |
| POST | `/payments/webhook` | **Stripe-Signature** (no JWT) | Stripe webhook receiver |
| POST | `/payments/:id/simulate` | owner, platform_admin | **Test only** (`ENABLE_TEST_ENDPOINTS=true`): play the customer's card step |

Other customers' payments return **404**.

### POST /payments/initiate

```json
{ "orderId": "6ad0da6d875f7b0a9623df81" }
```

Only `orderId` is accepted; `amount` or `currency` returns **400**. The Payment Service decides from its own data,
built from events (no calls to other services): the order's owner and deadline from `order.created`, closures from
`order.cancelled` / `order.expired`, and **the amount to charge from `billing.finalized.v1` (`finalAmount`)**.
Until Billing has finalized the amount, initiation returns **409 `BILLING_PENDING`** with `Retry-After: 2`; clients retry
(typically under a second after placing the order). The response's `payment` includes `amount`, `invoiceId` and `invoiceNumber`.

→ **201** (PaymentIntent created) or **200** (existing PaymentIntent reused: retry or duplicate click)

With Stripe, pass `clientSecret` to Stripe.js (`stripe.confirmPayment`). The client secret is never stored by the service.

| Failure | Response |
|---|---|
| amount not finalized yet (or the order is unknown to Payment) | 409 `BILLING_PENDING`, header `Retry-After: 2` (nothing charged) |
| order belongs to another customer | 404 `NOT_FOUND` |
| order expired, or its `expiresAt` has passed | 409 `ORDER_EXPIRED` |
| order cancelled or not `pending_payment` | 409 `ORDER_NOT_PAYABLE` |
| already paid | 409 `ALREADY_PAID` |
| payment processing | 409 `PAYMENT_PROCESSING` |
| Stripe unreachable | 503 `PAYMENT_PROVIDER_UNAVAILABLE` (retry safely; same idempotency key) |

Billing or Order Service down no longer causes a 503: Payment doesn't call them.

### Payment statuses

`pending` → `requires_action` → (`processing`) → `succeeded` → `refund_pending` → `refunded` / `partially_refunded`.
`failed` can be retried (back to `requires_action` on the **same** PaymentIntent). `cancelled` is terminal.
See [ARCHITECTURE.md §13.3](ARCHITECTURE.md#133-payment-state-machine).

### POST /payments/:id/refund (platform admin)

```http
POST /payments/6ad0e1f2a1b2c3d4e5f60718/refund
Authorization: Bearer <platform admin token>
Idempotency-Key: refund-2026-10-15-0001
```

```json
{ "amount": 20000, "reason": "Missing item" }
```

`amount` is optional and defaults to the full remaining amount. → **202** with the refund `{ id, amount, status: "pending", … }`.
Repeating the same key → **200** with the same refund (`Idempotent-Replayed: true`). The payment goes to `refund_pending`,
then `partially_refunded` / `refunded` once the provider confirms. One refund may be in flight at a time (`409 REFUND_IN_PROGRESS`).
Customers don't call this: **cancelling an order refunds it automatically**.

### POST /payments/webhook

Stripe sends events here. Signature verification uses the `Stripe-Signature` header over the **raw** body (the
official SDK, with timestamp tolerance against replays).

| Response | When |
|---|---|
| 400 `INVALID_SIGNATURE` | missing, invalid, forged or expired signature |
| 200 `{ received, eventId, result }` | verified; `result` = `applied` / `unchanged` / `stale` (out of order, ignored) / `unknown` (not our payment) / `anomaly` (amount mismatch, ignored) / `duplicate` |
| 5xx | our own transient failure. Stripe retries. |

Handled types: `payment_intent.processing`, `.requires_action`, `.succeeded`, `.payment_failed`, `.canceled`,
`refund.created`, `refund.updated`, `refund.failed`. Others are acknowledged and ignored.

### POST /payments/:id/simulate (test only)

```json
{ "outcome": "succeed", "deliveries": 1 }
```

`outcome`: `succeed` | `fail` | `succeed_refund_fails` | `processing` (mock only). With Stripe this confirms the PaymentIntent
using Stripe **test** PaymentMethods (`pm_card_visa`, `pm_card_chargeDeclined`, `pm_card_refundFail`). With the mock it simulates
the outcome, and `deliveries` (1–5) re-sends the same signed webhook to demonstrate duplicate delivery. → **202**; the state
changes only when the webhook arrives.

```json
}
```

`sequence` is the 1-based position in the order's history. `metadata` never contains OTPs or payment secrets.

**`catalog.restaurant.updated.v2`** (Catalog → Order read model): `restaurantId`, `catalogVersion`, `reason` (`change|snapshot`),
`name`, `status` (`active|inactive`), `isOpen`, `isPureVeg`, **`adminIds: string[]`**, the full `items[] { id, name, price, isVeg, isAvailable }`, `updatedAt`.
v2 replaced v1 (which carried a single `ownerId`) in Stage 8.2; v1 is retired: no longer published, unbound from the Order Service's queue, and
rejected as permanent (dead-lettered) if one ever arrives. Every assignment change bumps `catalogVersion`, so a late or duplicate snapshot can
never restore a removed administrator in the projection.

**`auth.user.deactivated.v1`** (Auth → Catalog), published through the Auth Service's transactional outbox when an **active** account is
deactivated (`PATCH /auth/users/:id/status {"isActive": false}`): `userId`, `role`, `deactivatedAt`, `deactivatedBy`. The Catalog Service
removes the user from every restaurant's `adminIds` **assigned before `deactivatedAt`** and publishes updated v2 snapshots. Deactivating an
already-inactive account publishes nothing; reactivation publishes nothing and restores **no** assignments. The Delivery Service also
consumes it: a deactivated agent gets no new deliveries and cannot go available until they sign in again after reactivation.

**`auth.user.deleted.v1`** (Auth → Catalog, Delivery), published through the outbox in the same transaction as `DELETE /auth/users/:id`:
`userId`, `role`, `deletedAt`. Never published when nothing was deleted. Catalog tombstones the id, removes it from **every** restaurant's
`adminIds` (no timestamp cut-off: ids are never reused) and publishes v2 snapshots; restaurants and menus are kept. Delivery permanently
blocks a deleted agent (no new assignments, cannot register or go available); delivery history is kept. Both consumers are idempotent.

Auth itself consumes `delivery.partner_assigned.v1`, `delivery.completed.v1` and `delivery.cancelled.v1` (queue `auth-service.delivery-events`)
to know which agents hold an active delivery.
**`catalog.sync_requested.v1`** (Order → Catalog) `{ requestedBy, reason, requestedAt }`: asks for a snapshot re-broadcast.

Since Stage 6 every envelope also carries `aggregateId` (the order id) and a `correlationId` (the request id, or the order id by default).
`order.confirmed.v1` gained optional `customerEmail` and `customerName` (used by Delivery only to address the OTP email).

**Delivery events** (published by the Delivery Service on `food.events`; consumed by the Order Service):

| Routing key | `data` | Order effect |
|---|---|---|
| `delivery.ready_for_pickup.v1` | `deliveryId, orderId, restaurantId, readyAt` | → `assigning_delivery_partner` |
| `delivery.partner_assigned.v1` | `deliveryId, orderId, agentId, agentName, agentPhoneMasked?, assignedAt` | → `partner_assigned` |
| `delivery.picked_up.v1` | `deliveryId, orderId, agentId, pickedUpAt` | → `out_for_delivery` |
| `delivery.location_reached.v1` | `deliveryId, orderId, agentId, reachedAt, otpExpiresAt` (**no OTP**) | → `location_reached` |
| `delivery.completed.v1` | `deliveryId, orderId, agentId, deliveredAt, otpVerified: true` (required) | → `delivered` |
| `delivery.cancelled.v1` | `deliveryId, orderId, previousStatus, reason, agentId?, cancelledAt` | delivery mirror only |
| `delivery.assignment_failed.v1` | `deliveryId, orderId, attempts, reason, failedAt` | delivery mirror only (no refund) |

**Restricted command** `notification.delivery_otp.v1` — exchange **`food.restricted`** (direct), never `food.events`; only
`delivery-service` may publish and only `notification-service` may consume (per-service broker users):
`deliveryId, orderId, orderNumber, customerId, customerEmail, customerName, agentName, otpSequence, otpCiphertext, otpExpiresAt`.
`otpCiphertext` = `v1.<ephemeral X25519 key>.<iv>.<ciphertext>.<tag>` (base64url; AES-256-GCM with an HKDF-SHA256 key), sealed to the
Notification Service's public key.

## Delivery Service

Gateway prefix `/deliveries`. Partner endpoints require a JWT with role `delivery_agent`; the partner is always the token's
subject (bodies are strict and never name an agent). Deliveries assigned to someone else return **404**; other roles **403**.
Customers don't call this service — they track orders through `/orders/:id/tracking`.

| Method | Path | Auth | Description |
|---|---|---|---|
| PUT | `/deliveries/agents/me` | delivery_agent | Register/update own partner profile: `{ "phone": "9845012301", "available": true }` (phone required the first time). Going offline while busy → 409 `AGENT_BUSY`. A deactivated account → 403 `ACCOUNT_DISABLED` (until a token issued after reactivation is used), a deleted one → 403 `ACCOUNT_DELETED` |
| GET | `/deliveries/agents/me` | delivery_agent | Own profile + `activeDelivery` (agent view) |
| GET | `/deliveries/agents` | platform_admin | All partners (`?status=available\|busy\|offline`) |
| GET | `/deliveries` | delivery_agent (own), platform_admin | List (`?status=&page=&limit=`) |
| GET | `/deliveries/:id` | assigned delivery_agent, platform_admin | Delivery (agent view) |
| GET | `/deliveries/order/:orderId` | platform_admin | Delivery for an order |
| POST | `/deliveries/:id/pickup` | assigned delivery_agent | `partner_assigned` → `picked_up` |
| POST | `/deliveries/:id/arrived` | assigned delivery_agent | `picked_up` → `arrived`; issues the OTP (emailed to the customer) |
| POST | `/deliveries/:id/verify-otp` | assigned delivery_agent | `{ "otp": "482913" }` → `delivered` |
| POST | `/deliveries/:id/resend-otp` | assigned delivery_agent | New code (supersedes the old one); cooldown + limit |
| POST | `/deliveries/:id/retry-assignment` | platform_admin | Re-queue a delivery whose assignment failed |

| Failure | Response |
|---|---|
| not the assigned partner / unknown id | 404 `NOT_FOUND` |
| not a delivery partner | 403 `FORBIDDEN` |
| pickup twice / arrival twice | 409 `DELIVERY_ALREADY_PICKED_UP` / `DELIVERY_ALREADY_ARRIVED` |
| arrival before pickup / verify before arrival | 409 `DELIVERY_NOT_PICKED_UP` / `DELIVERY_NOT_ARRIVED` |
| delivery cancelled / already delivered | 409 `DELIVERY_CANCELLED` / `ALREADY_DELIVERED` |
| wrong code | 422 `OTP_INVALID` ("n attempt(s) remaining") |
| 5th wrong code, or code locked | 423 `OTP_LOCKED` |
| code expired (default 5 min) | 410 `OTP_EXPIRED` |
| reissue within 30 s / more than 3 codes | 429 `OTP_RESEND_TOO_SOON` / `OTP_RESEND_LIMIT` |
| retry-assignment on a delivery that didn't fail | 409 `DELIVERY_NOT_RETRYABLE` |

`ASSIGNMENT_MAX_ATTEMPTS` (60), `ASSIGNMENT_TIMEOUT_MS` (600000), `OTP_TTL_MS` (300000), `OTP_MAX_ATTEMPTS` (5), `OTP_MAX_ISSUES` (3),
`OTP_RESEND_COOLDOWN_MS` (30000); secrets `OTP_HMAC_KEY`, `NOTIFICATION_OTP_PUBLIC_KEY`.

## Notification Service (internal)

No public API: it is not routed by the gateway and has no published port. It consumes `order.status_changed.v1` and the
restricted `notification.delivery_otp.v1` (dedicated `DELIVERY_OTP` template), and sends email through SMTP. Locally, every email is captured by **Mailpit**: UI at http://localhost:8025, API e.g.
`GET http://localhost:8025/api/v1/search?query=to:"priya@example.com"`. Nothing is delivered to a real mailbox.

## Quick curl walkthrough

Uses ids from the **full demo catalog** (Spice Route Biryani House). With only the sample catalog, take a restaurant id and a menu item id from
`GET /restaurants` and `GET /restaurants/:id/menu` instead.

```bash
G=http://localhost:8080
curl -s -X POST $G/auth/register -H 'content-type: application/json' \
  -d '{"name":"Priya Sharma","email":"priya@example.com","password":"Priya1234"}'
TOKEN=$(curl -s -X POST $G/auth/login -H 'content-type: application/json' \
  -d '{"email":"priya@example.com","password":"Priya1234"}' | node -pe 'JSON.parse(require("fs").readFileSync(0)).data.accessToken')
curl -s "$G/restaurants?city=Hyderabad&sort=rating"
curl -s "$G/restaurants/5d76d0a773b899a3c0c817b0/menu?availableOnly=true"
curl -s -X POST $G/orders -H "authorization: Bearer $TOKEN" -H 'content-type: application/json' -d '{
  "restaurantId":"5d76d0a773b899a3c0c817b0",
  "items":[{"menuItemId":"74a73ddec378d05239b6f639","quantity":2}],
  "deliveryAddress":{"line1":"12, Road No. 3","city":"Hyderabad","pincode":"500034"}}'
curl -s $G/orders -H "authorization: Bearer $TOKEN"
```
